Some Transactions need a resource that already exists. `utils.request` calls
another Transaction to create one.

## Addressing the call

`utils.request` is keyed by **Selector** — the same strings your hooks are
anchored to — and resolved through the same catalog, so the keys your editor
completes and the strings resolved at run time are the same strings by
construction.

```typescript
utils.request(
  selector,   // the Transaction to call
  args?,      // body, headers, query, path, cookies — overlaid on the generated request
  options?,   // runHooks, authorize
);
```

There is no `forStatusCode`: the Selector already carries the status.

## Seeding a resource

```typescript
import { beforeEach } from '@thymian/hooks';

export const seedLaunch = beforeEach(
  'GET /launches/{id} -> 200 (application/json)',
  async (request, ctx, utils) => {
    const created = await utils.request(
      'POST /launches (application/json) -> 201 (application/json)',
      { body: { missionName: 'Apollo 11', rocketType: 'Saturn V' } },
      { authorize: true },
    );

    if (created.statusCode !== 201) {
      utils.skip('could not create a launch to read back');
    }

    utils.setPathParam('id', created.body.id);
  },
);
```

`args` is overlaid on the **generated** request, so you only write the parts you
care about — the content type, the origin and everything else come from your API
description.

## What the response gives you

```typescript
{
  statusCode: 201,
  headers: { … },
  body: { id: 7, missionName: 'Apollo 11', … },
}
```

A JSON body is parsed for you, and after
[`thymian sampler init`](/references/plugins/sampler/hooks-api/#thymian-sampler-init)
it is typed by the Selector you asked for — so `created.body.id` is checked, and
a body field that stops existing is a compile error.

## The target's own hooks run

By default a nested request runs the target's own
`beforeEach → authorize → afterEach` pipeline, so seeding behaves like the real
run rather than like a second, quieter client. Your `authorize` hook applies to
it; so does any `beforeEach` that shapes it.

```typescript
await utils.request(selector, args, { runHooks: false });
```

`runHooks: false` sends the generated request as-is. Use it when you want the raw
request, and when you need to break a cycle.

<Aside type="caution" title="Authorization is per Transaction">
A nested request carries **its own** target's `authorize` flag, not the caller's.
Seeding a secured endpoint from an unsecured one needs `{ authorize: true }`;
and forcing it on still requires a registered `authorize` hook to supply the
credentials.
</Aside>

## Cycles fail loudly

Two hooks that seed each other would recurse until the stack gave out. Instead
the sampler refuses, and prints the chain:

```
A cross-endpoint request would re-enter "GET /launches/{id} -> 200 (application/json)", which is already running.
Try this:
  * The chain is:
      "GET /launches/{id} -> 200 (application/json)"
      → "POST /launches (application/json) -> 201 (application/json)"
      → "GET /launches/{id} -> 200 (application/json)"
  * Break the cycle, or pass `{ runHooks: false }` to seed from the raw request
    without running the target's hooks.
```

The chain is printed because `A → B → A` is usually a mistake three files apart,
and the middle of it is where the fix goes.

Nothing is sent before the refusal.

## Seeding once for the whole run

If a fixture is shared by every Transaction, `beforeAll` is cheaper than seeding
per request — and its returned closure is how the fixture gets cleaned up.

```typescript
import { beforeAll } from '@thymian/hooks';

export const seedOnce = beforeAll(async (utils) => {
  const created = await utils.request(
    'POST /launches (application/json) -> 201 (application/json)',
    { body: { missionName: 'Shared fixture' } },
    { authorize: true },
  );

  return async () => {
    await utils.request(
      'DELETE /launches/{id} -> 204',
      { path: { id: created.body.id } },
      { authorize: true },
    );
  };
});
```
